| `git-stash-reminder.sh` **blocked Stop forever on stashes holding nothing recoverable, and prescribed the opposite of the right remedy.** Since #2610/#2641 switched `auto-checkpoint.sh` to `git stash create` + `git stash store`, every checkpoint persists as a visible `git stash list` entry, so the hook's rare message became a recurring one. Three compounding gaps: the hook recorded nothing about what it had already reported, so reviewing a stash and consciously keeping it never cleared the block (only deleting the stash did) and the same entry re-blocked 13h 22m apart on two different days; the remedy was the hardcoded string `→ git stash pop`, which for a checkpoint whose tree equals the working tree is a no-op or a conflict, and in one observed case would have restored a deliberate mutation-test edit; and the script carried no disable variable at all, though eleven siblings did. | Four filters, all fail-toward-**reporting** so the fixes trade a repeated nag for information loss in neither direction: `CLAUDE_HOOKS_DISABLE_GIT_STASH_REMINDER=1` checked before anything else; a redundancy filter (`git diff --quiet <stash-sha>` — exit 0 means the stash's tree already equals the working tree) guarded by a **3rd-parent** check, since `git diff` cannot see an untracked payload and only `git stash push -u` creates one (`git stash create --include-untracked` does not, verified on git 2.43 — which is why auto-checkpoint stashes are exactly comparable); a report-once memory in a **sibling** `<baseline>.reported` file, keyed on commit hash so it survives `stash@{N}` reindexing (appending to the baseline itself would make a session stash indistinguishable from a pre-existing one and collide with defence 2's 0-byte path); and a provenance-chosen verb — "verify against the working tree, then `git stash drop`" for `auto-checkpoint before …`, `git stash pop` for anything else. The cheap hash/timestamp filters run first so the tree comparison runs only for survivors. | Same suite, grown 33 → **60 assertions**. Every suppression is paired: a redundant checkpoint → SILENT, **and the same stash → REPORT once the tree diverges** (so suppression is a property of the tree, not of the word "auto-checkpoint"); an already-reported stash → SILENT, **and a second, distinct stash → REPORT** while the first is not repeated and the count reads `Found 1` (so the memory cannot degenerate into blanket silence); the opt-out → SILENT, with both an unset control and a `=0` control → REPORT. The `-u` guard carries two asserted premises (the stash really has a 3rd parent; its tracked tree really does match the working tree) so the assertion cannot pass vacuously. Mutation-verified twice via the suite's `STASH_REMINDER_HOOK` seam: the pre-fix hook fails **11** of the new assertions, and deleting only the 3rd-parent guard fails exactly the two that pin it. The four pre-existing assertions that Stop twice on one stash now call a `forget_reported()` helper first, so they keep testing the #2306 baseline/age guards rather than being masked by the new memory. | issue #2686 |
