| `probe-delta.py` treated every missing or untrusted baseline as a silent first run (`FIRST_RUN=true`, nothing reported, a fresh baseline recorded) and offered no caller-side way to say "a baseline was expected". A scheduled workflow keeping its baseline in an evictable cache would therefore re-record silently on eviction and swallow every finding that appeared during the evicted window — the failure delta reporting exists to prevent, and the one #2554's decision says a cache miss must not produce. | `--expect-baseline`: a missing or untrusted baseline is a LOSS rather than a first run — every analyzer finding is re-reported beside a `baseline_lost` finding naming the cause (missing file vs. one recorded for another root/schema), `FIRST_RUN=false BASELINE_LOST=true`, and the baseline is re-recorded from the analyzer findings only. `BASELINE_LOST=` is emitted on every run so its absence never has to be interpreted. Without the flag the behaviour is unchanged. | `health-plugin/scripts/tests/test-probe-lib.sh` TEST i4 (control: without the flag a missing baseline stays a silent first run; with it: full re-report, `STATUS=WARN` on a warn-only set, `TYPE=baseline_lost`, re-recorded, and the next run reports `NEW=0 RESOLVED=0`; an untrusted baseline is named as untrusted; an error in the re-report stays `ERROR`; analyzer failure still outranks the flag) and TEST i5 (the class: every `Baseline.load` caller under `health-plugin/scripts/` must define `--expect-baseline`, read via the AST, with a non-vacuity assertion that a caller was found). Mutation-verified: ignoring the flag fails 14 assertions; recording the synthetic finding into the baseline fails exactly the `RESOLVED=0` one. | issue #2554 |
