| `scripts/check-context-command-execution.sh` (the `lint` job's "Execute context commands in a bare sandbox" step) intermittently FAILED PRs on files the PR never touched. Two causes: (1) a broken-pipe/pipefail race — the per-command classification used `printf '%s' "$err" \| grep -Eqi "$RE"`; with `set -o pipefail`, a `grep -q` that matched and closed the pipe early while printf was still writing a large stderr string made printf take SIGPIPE (141), so pipefail reported the pipeline non-zero and the `if` flipped, misclassifying an UNPARSEABLE/ENV_MISSING as FAIL nondeterministically; (2) false-positive extraction of `!`backtick`` strings that are not real Context commands — `gh-cli-agentic:299` (a `!`gh run view $ID …`` line inside a ```markdown documentation fence) and `binary-analysis:204` (a markdown table row where `` `Rar!` `` abuts the next cell's opening backtick, matching the `!`` pattern and executing `52 61 72 21 …\|…` → `syntax error near unexpected token '\|'`). | The three classification/deny greps were piped; and the extraction loop matched `!`` on every line with no fenced-code-block or table-row awareness. The fix replaces all three `printf \| grep -Eq` with here-strings (`grep -Eq "$RE" <<<"$x"` — no pipe, no pipefail/SIGPIPE race), and gates the extraction loop on a fenced-code-block toggle (``` / ~~~) plus a markdown-table-row skip (line starts with `\|`) — a real Context command is a `- <label>: !`<cmd>`` list item, never inside a fence and never a table row, so neither guard can drop a legitimate command. | `scripts/tests/test-check-context-command-execution.sh` F asserts a fixture whose only `!`backtick`` occurrences are inside a fence and a table row extracts NOTHING (`PASS=0`/`FAIL=0`/`UNPARSEABLE=0`/`ENV_MISSING=0` — a buggy harness would run the fenced gh command as ENV_MISSING and the table row as UNPARSEABLE); G asserts no `write error: Broken pipe` on harness stderr | issue #1744 |
