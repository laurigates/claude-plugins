| `agent-patterns-plugin:parallel-agent-dispatch` documented `isolation: "worktree"` exhaustively but said nothing about **`isolation: "remote"`**, and offered no way to notice that a remote dispatch had **run locally**. Three agents dispatched with `isolation: "remote"` all ran in local worktrees in the shared checkout; nothing in the dispatch tool result indicated the mode in effect. Two were killed by a 600s stall watchdog, and recovery followed the skill's "audit remote, then resume" protocol — `gh pr list` and `git ls-remote --heads origin`, both empty — so the work was reported to the user as unrecoverable. Twice. `git worktree list` showed the branch holding a **complete, unpushed** commit. The remote audit was accurate; the conclusion drawn from it was wrong, because the protocol assumes remote-dispatched work lands remotely. **An empty remote is evidence about the PUSH, not about the WORK**, and the two come apart exactly when an agent dies between committing and pushing — the likeliest single place to die, since the push is last. | Added an `isolation: "remote"` hazard section to `references/worktree-hazards.md` (the mode is a REQUEST that may resolve to a local worktree; the two tells are `git worktree list` and the completion notification's `worktreePath`), an "Audit local worktrees alongside the remote" section to `references/failure-recovery.md` (only remote-empty **and** no worktree **and** no unpushed commits **and** a clean tree supports "nothing landed"), wired into the existing usage-limit recovery protocol's `gh pr list` step, plus the draft-PR-early mitigation that actually worked (commit, push, open a **draft** PR before the bulk of the work, then push after each commit — the retry agent survived its own branch being merged and deleted mid-task on that basis; recovery was one cherry-pick).
