| `project-plugin/skills/project-init` carried `- GitHub CLI: !`which gh`` in its `## Context` block. `which` signals "not found" purely through its **exit code** — it exits 1 and writes **nothing** to stderr — and a non-zero exit from a Context backtick aborts the skill before its body runs. So `/project:init` was unusable for anyone without `gh` on PATH: precisely the fresh-machine case the skill exists for. Same abort class as #899 / #1205 / #1206 / #1351. Two things kept it invisible: `lint-context-commands.sh` had **no `which` rule** (it was the only `which` in a Context block repo-wide, so no prior burn added one), and the executing backstop `check-context-command-execution.sh` only fires when **the harness box itself** lacks the tool — on any developer or CI machine that has `gh`, the probe passes and the abort stays latent (verified: `--strict` reports `PASS=3 FAIL=0` here, and `FAIL=1 EXIT=1` with `gh` removed from PATH). | Moved the probe out of `## Context` into the skill body, run via the **Bash tool** where a non-zero exit is survivable, with an explicit availability report and an `--github` fallback — the capability check is kept, not dropped. A `find` over a fixed set of bin directories was rejected: it errors to stderr when a start directory is absent (the #1482 class, so it only moves the abort) and cannot see `gh` installed via mise/asdf/nix/cargo, yielding a false "not installed". | `lint-context-commands.sh` rule `which-in-context` (anchored to `^- .*!\`…\`` so `which` in fenced code, prose, or a table is not flagged); regression test `scripts/tests/test-lint-context-commands.sh` — the first test for this linter — pins the rule firing, the no-false-positive case, a clean block, the sibling `command-v-in-context` rule, and that no `which` remains in any Context block repo-wide.
