| `scripts/check-driver-freshness.sh` intermittently failed pre-commit with "dependency newer than driver's reviewed: date" when a dependency's `modified:` date EQUALLED the driver's `reviewed:` date — the non-reproducible #1704 symptom whose epoch diagnostics finally revealed a **1-second** gap between the two compared epochs for identical date strings. ROOT CAUSE: BSD `date -j -f "%Y-%m-%d" "<date>" +%s` fills the unspecified time-of-day fields with the *current* wall-clock time, so `driver_epoch` (parsed once up front) and each `dep_epoch` (parsed later in the loop) differ by 1s whenever the two `date` calls straddle a second boundary, making an equal date compare `-gt` (newer). The earlier #1704 work added the epoch diagnostics but never fixed the parse. | `date_to_epoch()` parsed a bare `%Y-%m-%d`, which is time-of-day dependent on BSD. The fix pins parsing to `00:00:00` (`date -j -f "%Y-%m-%d %H:%M:%S" "<date> 00:00:00"` on BSD; `date -d "<date> 00:00:00"` on GNU) so the epoch is a pure function of the date. | `scripts/tests/test-check-driver-freshness.sh` TEST C parses the same date twice across a forced `sleep 1` second boundary and asserts the epochs are identical (the determinism invariant); the `date_to_epoch_portable` test helper is pinned to the same midnight form so TEST B's `epoch <N>` assertions fail if the script regresses to current-time parsing. | issue #1704 |
