| `configure-release-please` (SKILL.md + `release-please-standards`) presented the legacy `MY_RELEASE_PLEASE_TOKEN` PAT as the single canonical release token, with no mention of the **GitHub App-token pattern** (`actions/create-github-app-token` → `RELEASE_PLEASE_APP_ID` var / `RELEASE_PLEASE_PRIVATE_KEY` secret) that is the laurigates org standard. gitops provisions the App credentials on `release_please = true` repos, so following the skill verbatim produced a PAT workflow that diverged from every other repo and never consumed those credentials; the compliance check would also flag a correct App-token workflow as needing the PAT. | The skill documented only the PAT form. The fix documents the App-token pattern as the **preferred** option in both skills (workflow templates, token-config table, installation, troubleshooting) and instructs the compliance check to treat an existing App-token workflow as compliant rather than flag it. | `plugin-compliance-check.sh` `check_skill_body()` — for `configure-release-please`, asserts the SKILL.md body retains both `create-github-app-token` and `RELEASE_PLEASE_APP_ID`. Dropping either would silently revert to PAT-only guidance. | issue #1789 |
