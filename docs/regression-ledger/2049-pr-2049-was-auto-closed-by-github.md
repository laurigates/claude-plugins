| PR #2049 was auto-closed by GitHub — never merged — and its work sat stranded on a branch, unnoticed. It was stacked on `feat/pi-tier-manifest` (base != `main`); when that base PR (#2048) was squash-merged and its branch deleted, GitHub closed the child instead of retargeting it, and **a closed PR whose base ref is gone cannot be reopened** (`gh pr reopen` → *"Could not open the pull request"*). A follow-up sweep found 26 dead branches, 2 of which carried real work that had **never had a PR opened at all** — so no `pull_request` event ever fired for them. | Nothing swept for "commits on a branch that never reached the default branch". An event-driven `pull_request: closed` workflow cannot fix this: by the time the event fires the base ref is already deleted (the reopen window is gone), it needs a caller file in **every** repo, and it is structurally blind to never-PR'd branches. Added a **scheduled sweep** instead — `scripts/check-stranded-work.sh` (takes `--repo`, so one run can sweep siblings) classifying each branch by PR fate: `stranded_autoclose` (closed-unmerged AND base ref 404s) and `stranded_no_pr` (commits, no PR, past a grace period), vs the three that must stay **silent**: `landed` (merged PR), `closed_deliberate` (closed-unmerged but base ref ALIVE = a human decision — 11 of the 26 were this), and `in_flight` (pushed within `--min-age-days`, default 7). Two traps encoded: `git cherry` (**not** `rev-list`/ancestry/tree-containment) detects patch-equivalence so a **squash-merged** branch isn't misreported as stranded; and the **base-ref-404 check is the sole discriminator** separating an accident from a deliberate close. | `scripts/tests/test-check-stranded-work.sh` drives the pure `classify` stage via `--fixture` (hermetic — no network, no `gh`, no remote) over all six branch shapes from the 2026-07-12 sweep, pinning the three NEGATIVE cases hardest: deliberate close (base alive) NOT reported, squash-merged branch (still "ahead" by SHA) NOT reported, and branch pushed today with no PR NOT reported (the live run flagged exactly this false positive). Wired into `.pre-commit-config.yaml`; the sweep runs weekly via `.github/workflows/stranded-work-audit.yml`, which opens one `stranded-work` issue and emits nothing when clean. | issue #2049 |
