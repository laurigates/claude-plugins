| `git-plugin:git-local-hazards` §1 said `git cherry` "survives squash and SHA rewriting". Reproduced on git 2.55: after a two-commit branch is squash-merged, `git cherry main <branch>` prints `+` for **both** commits, because no single commit's patch-id matches the combined squash commit. A single-commit squash prints `-` only while `main` left the diff's context lines alone: patch-id hashes context lines, so an upstream edit within them makes a fully landed commit read `+` (PR #2825 review, reproduced on git 2.43). §1's own scenario (commits added after a squash-merge) leaves exactly the multi-commit shape, so the recommended check cannot tell the orphan from the landed work. | §1 now says cherry survives SHA rewriting but not a squash-merge, and bounds the orphans by the PR's frozen head: `gh pr list --head <branch> --state all --json state,headRefOid`, then `git log --oneline <headRefOid>..<branch>`. The first version of this fix compared commit dates against `mergedAt`; the PR #2825 review showed that misses a commit made before the merge but pushed after it, which is dated earlier than `mergedAt`. | `scripts/plugin-compliance-check.sh` `check_skill_body()` errors when `git-local-hazards` loses the `multi-commit` caveat or the `<headRefOid>..<branch>` boundary. Mutation-checked: deleting either from the file turns the plugin's Body column ❌ and exits 1; restored from snapshot, it passes.
